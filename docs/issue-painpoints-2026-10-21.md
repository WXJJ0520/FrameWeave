# 原项目用户反馈与本轮优化依据

核查日期：2026-10-21。来源为 ATH-MaaS/Pixelle-Video 公开 Issues；本地对照仅阅读代码，不读取密钥、不提交生成任务。本文记录调研和建议，不代表这些上游问题已在本机复现或已被本轮修复。

<!-- 维护说明：保留来源日期、证据等级与本地现况，避免把用户推测写成已证实根因。 -->

## 结论

优先改善既有创作页面的填写顺序、配置说明、连接诊断与失败提示。用户的主要障碍是“不知道该配哪项”“测试失败后不知道检查哪里”“生成到后半程才发现依赖或工作流不满足”，不需要为此增加新的创作模块。

## 七类痛点

### 1. ComfyUI 连接失败，反馈不能帮助定位

- **来源与日期**：[连接测试失败 #239](https://github.com/ATH-MaaS/Pixelle-Video/issues/239)，2026-08-05；2026-10-07 仍有用户追问。
- **用户反馈**：填写 ComfyUI 密钥后测试失败，后来有人误以为整个 ComfyUI 路线不能使用。
- **证据边界**：没有网络日志或维护者确认的根因；“解决不了”是普通评论者的意见，不能作为事实。
- **本地现况**：核查时 `web/components/settings.py` 的 ComfyUI 测试只 GET `/system_stats`，没有使用当前表单的 API Key；非 200 只给通用失败信息，异常直接展示。这个具体代码问题值得修正，但不能据此断言就是该 Issue 的原因。
- **本轮适合改善**：分别提示地址格式、无法连接、鉴权拒绝、服务端错误、返回格式异常；如果部署需要鉴权，使用与实际 ComfyUI 客户端一致的鉴权方式。成功文案应说明“服务可访问”，不承诺所有工作流可运行。错误详情脱敏。
- **本轮已落实（2026-10-21）**：测试使用当前表单地址与 Bearer 密钥，认证方式与本机 ComfyKit 客户端一致；分类处理格式、DNS、拒绝连接、连接或读取超时、证书、401/403、404、502/503/504、重定向及异常返回格式。合法反代子路径保留；以 `/v1` 结尾只提醒，不擅自改写。结果不包含原始异常或响应体，表单重渲染后旧结果消失。只读查询不保存配置、不提交工作流、不自动重试。

### 2. Ollama / 中转站的基础地址和代理关系不清楚

- **来源与日期**：[本地 Ollama 配置提示 502 #255](https://github.com/ATH-MaaS/Pixelle-Video/issues/255)，2026-09-06。
- **用户反馈**：本地已安装模型，但连接测试及加载模型都返回 502。
- **证据边界**：Issue 未提供服务日志、代理状态或部署拓扑，无维护者结论。不能把 502 直接解释为 Key 错误，也不能仅凭用户文字认定 `/V1` 大小写是根因。
- **本地现况**：已有基础地址归一化及 `/models` 查询；媒体提供商的诊断较完整，LLM 查询仍有自己的错误处理。两处提示语和测试结果含义应统一。
- **本轮适合改善**：在原地址输入框旁提供 `http://127.0.0.1:11434/v1` 示例；明确填写基础地址，不填写完整聊天接口。针对 502 提示检查反向代理/上游服务，针对容器说明 localhost 指向运行应用的环境。模型目录查询成功只证明目录接口可达，不证明生成权限。
- **本轮落实边界**：已补充文本模型使用 OpenAI 兼容接口、与原生 ComfyUI 不同及“测试不保存”的说明；未重写 LLM 连接诊断，也未验证 Issue 提报者的 Ollama 部署。

### 3. 数字人口播和动作迁移后半程失败，用户不知道是哪一步

- **来源与日期**：[数字人口播生成失败 #240](https://github.com/ATH-MaaS/Pixelle-Video/issues/240)，2026-08-06；[工作流未返回视频 #216](https://github.com/ATH-MaaS/Pixelle-Video/issues/216)，2026-06-20。
- **用户反馈**：#240 明确说第二步未返回视频，并说明已设置 LLM 和 RunningHub Key；#216 只有通用“工作流没有返回视频”的错误。
- **证据边界**：没有完整工作流响应或已确认根因。不能认定这是 LLM 模型问题，也不能说 RunningHub 普遍不可用。
- **本地现况**：数字人页面本来就有前置图片、配音、口播视频等不同配置；业务异常仍存在英文通用提示。多个阶段分散摆放，容易让用户把“配好一个 Key”理解成整条流程已准备好。
- **本轮适合改善**：沿用原流程，明确展示“人物/文案 → 配音 → 口播视频”的填写层级；将所需服务说明放在对应字段旁。失败时显示阶段名称、工作流名称和下一步检查项，保留用户已有输入。不要自动重提可能计费的生成任务。
- **本轮已落实的有限改进（2026-10-21）**：数字人口播在实际调用处记录准备、前置图片、文案、配音、口播视频、结果获取、作品记录和展示阶段；错误提示指出已知阶段并给出对应检查建议。工作流返回结果却没有视频地址时单独说明；视频已生成但作品记录保存失败时明确区分，避免误导用户重新生成。原服务区增加三步职责说明，没有新增模块。
- **反馈边界**：诊断折叠区只显示固定阶段、异常类型和合法 HTTP 状态码，不展示原始异常 URL、请求参数或 traceback；未知阶段明确说明无法定位，不猜测具体根因。没有改变服务调用参数、工作流、重试策略，也未调用真实生成。已用离线替身执行各关键分支验证阶段归属、停止后续调用与脱敏行为；这不等于解决所有上游视频服务故障。

### 4. 界面出现本地选项，实际上没有配套工作流

- **来源与日期**：[找不到 digital_combination.json #229](https://github.com/ATH-MaaS/Pixelle-Video/issues/229)，2026-07-10；贡献者于 2026-07-15 回复修复情况。
- **维护者侧证据**：贡献者解释原数字人流程保留了 SelfHost 选项，却未提供对应本地 ComfyUI 文件；新版本删除该选项并改用 API。Issue 仍处于 Open，不等于该旧选项缺陷仍未处理。2026-10-18 的用户评论另称 RunningHub 也跑不通，但没有详细证据。
- **本地现况**：`web/pipelines/digital_human.py` 已按对应工作流文件是否存在构建服务选项，避免直接展示缺失的本地工作流。这项防护已经存在。
- **本轮适合改善**：保留按能力显示选项的规则；用简短说明告诉用户本地服务不是所有流程都支持。若文件在选择后被移走，再给出准确的缺失文件提示。不要把“重新加回无工作流选项”当成恢复功能。

### 5. 终端有 FFmpeg，但应用运行环境仍找不到

- **来源与日期**：[No ffmpeg exe could be found #225](https://github.com/ATH-MaaS/Pixelle-Video/issues/225)，2026-07-04。
- **用户反馈**：使用 v0.1.15 Windows 整合包，应用报缺少 FFmpeg，但 cmd 能打印版本。
- **证据边界**：报告支持“终端与应用的检测结果不一致”，不能确定具体是 PATH、虚拟环境还是 imageio 配置导致。
- **本地现况**：现有启动脚本已有 FFmpeg/ffprobe 检查，但脚本检查不能替代实际 Python 进程及相关库的检测。
- **本轮适合改善**：在原系统配置或启动诊断中呈现当前进程可用的 FFmpeg、ffprobe 和语音依赖状态；缺失时给对应环境的修复说明，避免等到生成末尾才发现。单纯找到可执行文件不应标为整条生成链路验收通过。

### 6. Edge TTS 外部服务拒绝，长时间重试后仍只有原始异常

- **来源与日期**：[新的 BUG / Edge TTS 403 #260](https://github.com/ATH-MaaS/Pixelle-Video/issues/260)，2026-10-19。
- **用户反馈**：403 后多次重试失败；提报者称升级所在环境里的 edge-tts 后恢复。
- **证据边界**：升级后恢复是提报者自述；“微软 10 月强制 V2”来自其 AI 推测，不是官方公告，本文不采用该根因说法。
- **本地现况**：`pyproject.toml` 已固定 `edge-tts==7.3.1`；`pixelle_video/utils/tts_util.py` 已对 401/403 停止重试并给出脱敏中文提示。这是本地已有改善，不应重复算作本轮新功能。
- **本轮适合改善**：把“本地合成”解释为调用在线 Edge TTS，避免误以为离线服务；保留现有试听入口和拒绝即停止重试行为。提示检查当前虚拟环境依赖与网络，不要求用户填写无关 API Key。

### 7. Windows 整合包和代码版本不同，用户不知道自己使用哪个版本

- **来源与日期**：[没有最新版 Windows 一键整合包 #257](https://github.com/ATH-MaaS/Pixelle-Video/issues/257)，2026-09-07。
- **用户反馈**：提报时认为整合包仍停留在早期版本。
- **证据边界**：这是一条发布渠道体验反馈，不能由它推断今天的最新 Release 状态；本次没有对所有发布包作版本核对。
- **本地现况**：当前二开已有统一启动脚本，但上游包更新节奏属于外部维护范围。
- **本轮适合改善**：在原配置页的帮助区域显示本地应用版本与启动方式，把“界面改版”“依赖更新”“生成模型是否可用”分开说明。保留一份清晰的本地启动/升级文档，不额外开发包管理模块。

## 实施优先级与验收范围

| 优先级 | 在原功能内优化 | 可以本地验证什么 | 不能据此声称什么 |
| --- | --- | --- | --- |
| P0 | 系统配置按用途分组，基础地址和测试含义说明 | 字段完整、值可保留、读写不串提供商 | 所有第三方模型都可生成 |
| P0 | ComfyUI 与 LLM 连接测试分层反馈 | Mock 401/403/404/502/超时、地址校验、无敏感信息泄露 | 上游 Issue 的唯一根因已查明 |
| P1 | 数字人等原流程的步骤排版及阶段错误说明 | 原入口都在、表单状态不丢、缺失条件反馈明确 | 已完成收费数字人生成验收 |
| P1 | 当前进程的依赖信息和失败引导 | 本机文件/版本/可执行文件检查 | 离线环境可使用在线 TTS |
| 既有能力保持 | 缺失工作流过滤、TTS 拒绝停止重试、媒体连接诊断 | 回归检查既有保护行为 | 这些都是本轮新增 |

本次筛选优先使用正文含明确操作、错误或维护者回复的 Issue。列表中只有人名、单词或无复现信息的帖子未作为产品痛点证据，也没有据此统计“高频率”或声称代表全部用户。

上述优先级包含后续建议，不是全部已完成清单。FFmpeg 当前进程诊断及版本信息整理尚未在本轮实施；数字人阶段反馈只覆盖页面可以直接观察到的调用边界，API 客户端内部的生成和下载仍可能共用“口播视频”阶段。
